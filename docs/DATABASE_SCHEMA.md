# Database Schema

## Purpose

This document defines the logical database schema for Momenta.

The schema is designed for:

* offline-first operation
* future sync readiness
* widget support
* reminder support
* auditability
* long-term maintainability

This document describes logical ownership.

Actual SQLite implementation may evolve through migrations.

---

# Database Principles

Momenta uses:

* SQLite
* migration-based schema evolution
* repository access only

Rules:

* no direct UI database access
* no business logic in persistence layer
* all schema changes require migrations
* ids are stable
* soft delete preferred over destructive delete

# Soft Delete Policy

Entities should support:

deletedAt

instead of destructive deletion whenever practical.

Benefits:

* recovery
* undo
* safer migrations

---

# Import / Export Compatibility

Every exported file must contain:

schemaVersion

Example:

v1

v2

v3

# Data Ownership

Moment owns:

* reminder plans
* widget relationships

Category owns:

* category metadata

Settings own:

* user preferences

AuditLog owns:

* operational history

Ownership must remain clear.

---

# Schema Evolution Rule

Every schema modification requires:

1. migration
2. migration test
3. rollback consideration
4. version update

No direct schema mutations.

---

# Final Rule

The schema should be optimized for:

* clarity
* stability
* maintainability
* future growth

before optimization for complexity.
